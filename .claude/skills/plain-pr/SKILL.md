name: plain-pr
description: 撰寫或更新 pull request（PR）內文時使用。讓只懂一點軟體的 reviewer 也能從「會造成什麼結果」來判斷這個 PR。
---

致謝：改編自 Matt Pocock 的開源 repo github.com/mattpocock/skills 中的 pr skill，該 skill 以 Dex Horthy（HumanLayer）的 show-me skill 為基礎。

讀者：讀者是作者的主管。主管看得懂一些程式碼，只是看得慢。主管已經懂「網頁」「資料庫」「上線」這類詞。比較深的前端概念會讓主管看不懂，例如 state / 狀態管理、CSS、hydration。

PR 內文用繁體中文寫。檔名、指令名稱和程式碼裡的名稱保持原樣。不要寫開場白。整篇內文要能在一分鐘內讀完。

讀者沒辦法判斷程式碼寫得好不好，但能判斷三件事的結果：行為有沒有照我們想要的方式改變、能不能復原、誰可能受影響。每個段落都回答其中一件。

使用下面的範本：

## 改了什麼
一句讀者能轉述給別人聽的話，說明使用者或系統之後會有什麼不同。
一個日常生活的比喻，最多兩句，只在能讓改動更清楚、而且不會誤導時才寫。
選填：用最小的篇幅呈現動到了什麼，用日常的名稱寫成簡短的「改之前／改之後」清單。

## 怎麼確定它能用
- 改之前：改動前會發生什麼（如果改動看得到，附截圖）。
- 改之後：現在會發生什麼（看得到就附截圖）。
- 我怎麼檢查的：實際跑過的檢查和結果，用一句白話寫。如果什麼都沒跑，寫「未驗證」，並告訴讀者可以自己試什麼。

## 合併前請看
- 能不能復原：可以，很容易／可以，但要花點功夫／不行。用一句話說原因。
- 誰或什麼可能受影響：一個短語，例如「只有設定頁」或「每個使用者存的資料」。
- 我的建議：直接核准／仔細看一個地方（說是哪裡）／先問工程師。用一句話說原因。

## 學一個概念
挑一個這次改動裡出現、讀者之後很可能會再遇到的技術名詞，用兩三句話解釋，並跟這個 PR 連結起來。

規則：
1. 寫結果，不寫程式碼。不要一行一行講解程式碼。
2. 證據：改動看得到時，截圖是最好的證據；其次是測試或指令的執行結果。沒測過就絕對不要說測過。
3. 「難以復原」指的是：刪除或搬移資料、寄送訊息／email／款項給真實的人、改變誰能存取什麼、公開發布內容，或改動其他系統依賴的東西。其他大多數改動都能靠 revert 這個 PR 復原。
4. 技術名詞避不掉時，第一次出現要用括號解釋。
5. 如果你看得到之前的 PR 內文，挑一個它們還沒教過的概念。
